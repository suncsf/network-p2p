# 大文件续传修复

> 归档日期：2026-11-27 ｜ 类型：缺陷处理（feedback） ｜ 来源：AI 编码会话（OpenCode + GLM） ｜ 梳理汇入时间：2026-11-27

## 用户提示词（原话，一字不改）

> Error occurred in handler for 'transfer:resume': Error: 接收端拒绝：无效 token
>     at sendFiles (file:///F:/project/network-p2p/out/main/index.js:1180:11)
>     at async LatticeServer.executePush (file:///F:/project/network-p2p/out/main/index.js:1890:7)
>     at async LatticeServer.resumePush (file:///F:/project/network-p2p/out/main/index.js:1959:5)
>     at async TransferRunner.resume (file:///F:/project/network-p2p/out/main/index.js:562:7)

> 续传失败：Error invoking remote method 'transfer:resume': Error: 原连接已断开，无法续传，请在文件页重新发起

（另附 dev 日志中连续 6 次「该传输正在进行中」的续传 CONFLICT 报错）

## 实际需求梳理

1. **>4GB 文件传输必中断**：用户的大文件（>4GB）传输到 4GB 附近中断，且续传在同一位置再失败，需要根因修复而非绕过。
2. **续传必失败**：点续传报「接收端拒绝：无效 token」「该传输正在进行中（CONFLICT）」「原连接已断开」三类错误，续传功能实际不可用。

## 问题与根因

### 1. >4GB 中断（协议层 bug，commit 7e8756b）

- 根因：`encodeChunk`（`src/main/p2p/transfer.ts`）分块偏移量用 **UInt32** 编码，上限 4294967295 字节（4GB-1），文件超过 4GB 后下一块抛 `RangeError`；续传到同一位置再越界再失败。
- 修复：**P2P 协议升级 v2**——CHUNK 帧（8→12 字节头）与 ACK 帧（12→16 字节）偏移量改 **BigUInt64**（上限 8EB）；`src/shared/p2p-frames.ts` 加 `P2P_VERSION = 2`，`FrameParser` 增加**协议版本校验**，新旧版本混连明确报「协议版本不匹配，请两端都更新」。
- 新增回归测试：`encodeChunk(1, 2**32 + 65536, …)` 验证 BigUInt64 编码（`p2p-e2e.test.ts`）。

### 2. 续传必 CONFLICT（自撞，commit 7e8756b）

- 根因：`preparePush` 对 `state === 'active'` 的已有记录一律拒绝；而 `runner.resume` 先把记录置 `active` 再调 `preparePush`，**自己撞自己**。
- 修复：改为仅当存在活跃推送任务（`pushJobs.has(sessionId)`）才算冲突；「已标记 active 但任务不在」是续传预置状态，放行。

### 3. 续传「无效 token」（接收端授权过期，commit 7919c5d）

- 根因：传输授权 grant 只有 5 分钟滑动有效期。发送端单方面点续传时直接拿原 sessionId 当 token 连接收端，接收端 `validateToken` 查无 grant → 拒绝。
- 修复：`validateToken` 增加 `resume` 参数——续传连接（HELLO 带 `resume: true`）且同会话接收记录存在且未完成时，自动从记录续传上下文（保存目录）**重建接收授权**（`createLocalTransferGrant` 同 token），记审计日志 `transfer:auto-resume-grant`；普通新连接仍严格要求有效 grant。效果：**任何一端点「续传」都能直接续**，不再要求接收端先手动授权。

### 4. 续传「原连接已断开」（死绑 connId，commit 4cc79bb）

- 根因：续传上下文只存创建时的 `connId`，应用重启后连接 id 全部变化，`resume` 必然报「原连接已断开」。
- 修复（`src/main/transfer-runner.ts`）：新增 `resolveConn`——优先原 connId，失效后按 **host/port/username 匹配现存连接**，最后按对端用户名兜底；`UploadResume`/`RecvResume` 增加端点字段（`prepareReceive` 与 `startUpload` 落库时写入）。「原连接已断开」仅在确实没有任何可用连接时报。

## 涉及文件

`src/main/p2p/transfer.ts`、`src/shared/p2p-frames.ts`、`src/main/server/service.ts`、`src/main/transfer-runner.ts`、`src/main/index.ts`、`src/main/p2p-e2e.test.ts`

## 验证与提交

typecheck 0 错误、42 项测试全绿（含 >4GB 编码回归）。提交 7e8756b、7919c5d、4cc79bb，均已推送 GitHub。

**重要约束**：协议升 v2 后**两端必须同步更新**（Ubuntu 100.5 `git pull` 重启），否则版本校验拒绝连接；4GB 中断记录需两端更新后续传。

## 2026-11-27 第七轮：批量下载续传「非法路径」修复（追加）

> 归档日期：2026-11-27 ｜ 类型：缺陷处理（feedback） ｜ 来源：AI 编码会话（OpenCode + GLM） ｜ 梳理汇入时间：2026-11-27

### 用户提示词（原话，一字不改）

> 传输与工作区连接分离，传输使用独立连接，就是关闭工作区连接，不影响正在传输的文件，只要服务端正常就可以继续传输和断点续传

> 现在断点续传会出现非法路径的错误

### 实际需求梳理

1. **续传报「非法路径」**：断点续传（发送端面板点「续传」）报 `PathViolationError: 非法路径`，需根因修复。
2. **传输与工作区连接分离**（同会话提出，**未实施，待办**）：传输使用独立连接，关闭工作区连接不影响正在传输的文件；只要对端服务端正常，传输与断点续传都能继续。仅完成代码勘察（`transfer-runner.ts` 目前复用工作区 `ConnectionManager` 连接发 RPC），未写任何代码。

### 问题与根因（用真实 TransferRunner 双端测试逐场景复现定位）

**主因（非法路径）**：批量下载走 `p2pPush { paths: [...] }`（不带 `path`），而发送端 `p2p-send` 记录的续传上下文只在**多于 1 项**时才存 `paths`（`paths: targets.length > 1 ? targets : undefined`）。单选批量下载的上下文里 `path` 与 `paths` 双双为空 → 发送端续传 `resumePush → preparePush → targets = [p.path!] = [undefined]` → `collectForTransfer(root, undefined)` → `resolveSafePath` 抛「非法路径」。报错堆栈：`TransferRunner.resume → resumePush → preparePush → collectTargets → FileOps.abs → path-safety.ts:16`。

**顺带发现并修复的两个相邻缺陷**（同根因家族）：

1. **多选批量下载续传丢文件**：接收记录（`p2p:prepareReceive`）续传上下文只存第一个选中项的 `path`，续传只补第一项，其余项静默丢失（测试中 `notes.txt` 永远不到）。
2. **对端主动推送的接收记录续传报「权限不足」**：`createRecvRecord` 的上下文只有 `{ dir }`，无对端 root/paths，接收机续传时以 `undefined` 调 `p2pPush`，被对端以 FORBIDDEN 拒绝，报误导性的「权限不足」。

### 解决方案

- `src/main/server/service.ts` `preparePush`：续传上下文**始终**存完整 `paths: targets`；targets 为空时明确报「缺少传输路径，无法续传，请重新发起传输」（BAD_REQUEST），不再让 `undefined` 流入 `resolveSafePath`。
- `src/main/index.ts` + `src/renderer/.../FilesView.vue`：`p2p:prepareReceive` 新增 `paths` 参数并写入接收记录续传上下文；`downloadSelected` 传入 `items.map(i => i.path)`。
- `src/main/transfer-runner.ts`：`RecvResume` 增加 `paths?`；接收侧续传按原 `paths` 重放（`paths` 优先、旧记录回退单 `path`）；对端推送记录缺少对端路径时明确报「该记录缺少对端路径信息，无法在本机续传，请在对端（发送方）续传」。

### 兼容性说明

修复前已中断的旧记录：单选批量的发送端记录上下文已缺失，续传会得到明确报错提示重新发起，无法自动恢复；多选批量的接收旧记录续传仍只补第一项。新发起的传输不受影响。

### 测试

新增 `src/main/transfer-resume.test.ts`（双端真实 TransferRunner + 两个 LatticeServer 实例，6 场景）：S1 上传断开重连续传、S2 单文件下载（带 rename）续传、S3 多选批量下载续传（全部文件到位）、S5 对端推送记录续传（明确报错）、S6 发送端 resumePush 续传、S7 单选批量发送端续传（「非法路径」回归）。
