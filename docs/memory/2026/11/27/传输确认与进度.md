## 实际需求梳理

1. **下载确认权归属**：Ubuntu（100.5）作为客户端从 Win11（100.3，本机调试运行的服务端）下载文件时，确认提示应弹在**文件所有方（100.3 服务端）**，而不是发起下载的 100.5 自己"确认自己的下载"。
2. **下载记录完整**：所有下载都要在传输面板留记录（此前 ≤8MB 小文件走 readFile+浏览器下载，完全无记录）。
3. **接收端终态感知**：服务端拒绝/超时/推送失败时，发起方的 p2p-recv 记录不能永久卡「进行中」。
4. **被连接提醒**：有客户端登录本机服务端时要弹通知。
5. **传输速度**：传输面板进度列实时显示速度与剩余时间。
6. **双端进度一致**：发送端与接收端的百分比显示应一致（尤其续传场景）。

## 方案与实现

### 下载确认权转移到服务端（commit ec30420）

- 根因：下载的 P2P 接收端就是发起方本机，接收确认逻辑（`createReceiveServer.requestConfirm`）在发起方触发，文件所有方全程无感知。
- 修复（`src/main/server/service.ts`）：
  - `handleP2pPush` 推送前经 `TransferManager.request()` 走「待确认的传输」流程；拒绝/超时（默认 60s）发送记录落「已取消」；`resume:true` 且已有发送记录时沿用既有授权免二次确认。
  - 发起方本机主动下载的接收授权标记 `preAuthorized`（`createLocalTransferGrant`），`requestConfirm` 直接放行并更新 total，不再自己确认自己。
- 本机 UI 事件转发（`src/main/index.ts`）：`LatticeServer` 新增 `onLocalEvent` 钩子（TransferManager emit → broadcast + onLocalEvent），因**本机渲染层不是自己服务端的 WS 客户端**，`transfer:incoming` 原本只广播给 WS 会话、本机永远收不到。转发后弹系统通知「收到下载请求」+ 悬浮球闪烁。
- `FilesView.vue`：下载统一走 P2P（删除 ≤8MB readFile+浏览器下载分支）；文案改「已发起下载，等待对方（服务端）确认后开始」。

### 关键缺陷与修复（feedback）

1. **主进程改动不生效（根因级）**：`electron-vite dev` 默认只热更新渲染进程，**主进程文件变动不重新编译**——服务端确认逻辑改完后 100.3 一直跑旧代码，所以「根本就没出现过确认消息」。修复：package.json dev 脚本加 `--watch`。教训：**调试主进程改动必须 `--watch` 或手动重启 dev**。
2. **接收记录卡「进行中」**：服务端拒绝/失败只广播 `transfer:progress` 事件，无人更新接收记录。修复：主进程 ConnectionManager onEvent 里对 `cancelled/failed` 把同 sessionId 的 p2p-recv 记录落终态。
3. **客户端登录无提醒**：`handleLogin` 成功后经 `onLocalEvent` 发 `client:login` 事件（用户名+来源 IP，去 `::ffff:` 前缀），主进程弹「客户端已连接」通知 + 悬浮球闪烁（commit 0e73b6f）。

### 传输速度与双端进度一致（commit 47de6cb）

- 速度显示（`TransfersView.vue`）：渲染层由 `transfer:updated` 进度差计算，EWMA 平滑（prev*0.6+instant*0.4，采样间隔 ≥200ms），进度条下显示 `12.3 MB/s · 剩余 1m20s`；进度回退（续传重置）自动重建基线。
- 进度语义统一为**接收端已落盘**（`p2p/transfer.ts`）：
  - 根因①：发送端按「已写入 socket 缓冲」计进度（瞬间冲 100%），接收端按落盘计；
  - 根因②：续传时发送端计入断点前字节、接收端从 0 开始（发送 100% 时接收只到 40%）；
  - 修复：发送端进度改由 **ACK 帧驱动**（acked += ACK 的 length，含续传基线），接收端 MANIFEST 续传分支把磁盘已有字节计入 `received` 基线。

## 同日追加：接收确认补漏 + 确认先行（commit 4cc79bb）

## 用户提示词（原话，一字不改）

> 接收策略 需要确认，但是这边没有提示确认直接就传输了

> 其次确认时，服务端不可能一直在连接对方，你的确认方式是先连接对方才能去确认，合理吗？

> 你不要启动软件，我自己run

## 实际需求梳理

1. 接收策略设为「需要确认」后仍有传输**未弹确认直接落盘**——找出漏网路径补上。
2. 用户设计质询：确认不应依赖「对方先连进来挂着等」——**确认先行，数据连接后行**。
3. 流程约束：AI 不要代跑 dev，由用户自己运行。

## 漏网路径排查结论

- **WS 上传（`uploadInit`/`uploadChunk`，经命令通道）完全没有确认环节**——只校验 UPLOAD 权限，直传落盘。这就是「设了需要确认却直接传了」的原因。
- P2P 下载方向（拉取）已是确认先行（服务端确认后才向外推送数据）。

## 方案与实现

1. **WS 上传确认**（`src/main/server/service.ts`）：`uploadInit` 落盘前先经 `TransferManager.request()` 确认，拒绝/超时报 FORBIDDEN 不落盘；同账户同路径 5 分钟滑动免二次确认（`wsUploadApproved` 缓存），传输中断自动重初始化不重复弹窗。
2. **接收方向授权确认先行**：`transferGrant`（direction='receive'，对方要往本机推文件）改为**授权时先弹确认、接受后才发 token** 并标记 `preAuthorized`——发送方连接进来直接传、不再二次确认，**无需挂连接等待**；拒绝/超时直接 FORBIDDEN。协议 `TransferGrantParams` 增加 `fileName`/`fileCount`/`totalSize` 概要字段供确认卡片展示。
3. 确认等待走对方**已登录的普通会话连接**（RPC 挂起等回复），不占专用数据连接；注意确认超时不宜超过客户端 RPC 30s 上限。
4. 回归测试：`p2p-e2e.test.ts` 新增 3 项——autoAccept=false 时 `uploadInit` 未确认被拒（FORBIDDEN 且不落盘）、接收方向 `transferGrant` 未确认被拒不发 token、下载方向（send）不受接收确认影响。
