# 大文件误取消修复

> 归档日期：2026-11-27 ｜ 类型：缺陷处理（feedback） ｜ 来源：AI 编码会话（OpenCode + GLM） ｜ 梳理汇入时间：2026-11-27

## 用户提示词（原话，一字不改）

> 传50、60GB的文件或者文件夹有时会主动取消

> 总结归档

## 实际需求梳理

1. 传输 50~60GB 的单个文件或文件夹时，传输记录会**在没有用户操作的情况下**变成「已取消」，需要排查全部会把记录自动标「已取消」的代码路径并根因修复。
2. 「有时」说明是条件触发的超时/竞态类问题，与传输体积正相关。

## 问题与根因（4 处叠加，均随体积变大更易触发）

### 1. 发送前全量 SHA-256（最大嫌疑）

- `sendFiles`（`src/main/p2p/transfer.ts`）在**连接对端之前**对每个文件完整读盘计算 SHA-256；而接收端 `createReceiveServer` 处理 CHUNK/DONE 时**从不校验**该哈希，纯属浪费。
- 50~60GB 在机械盘上要空转 5~10 分钟，期间进度 0%，且白耗授权有效期窗口。

### 2. 接收授权仅 5 分钟有效期

- 授权在 `p2p:prepareReceive`（下载发起时）就发放（`createLocalTransferGrant` / `handleTransferGrant`，`expiresAt = now + 5min`），此后要经过「对端枚举文件夹 → 对端点确认（≤60s）→ 哈希完」才发 HELLO；滑动续期只在握手成功后生效，第一次 HELLO 前时钟一直在走。
- 任何一步拖过 5 分钟 → token 过期 → `validateToken` 拒绝 → 「无效 token」→ `executePush` 把发送记录标**已取消**，并广播 `cancelled` 让接收记录也变**已取消**（`src/main/index.ts` 496-506）。

### 3. p2pPush RPC 固定 30 秒超时

- `LatticeClient.request` 写死 30s 超时；`handleP2pPush` 要等 `preparePush`（`collectTargets` 递归枚举整个文件夹 + 逐文件 stat）完成才 reply。
- 大文件夹（几万文件/机械盘冷缓存）枚举超 30s → 客户端报「请求超时」→ 渲染层调 `transfer:fail`（`src/main/index.ts` 406-411）把接收记录标**已取消**。`runner.resume` 的 p2pPush 调用同样受影响。

### 4. 失败状态误判「已取消」丢断点

- `executePush` 用「本次会话是否收到过 ACK（sentBytes）」区分 cancelled/interrupted：S6 回归测试暴露竞态——发送端已把数据写入 socket，但接收端销毁连接时 ACK 尚未被发送端处理，`sentBytes = 0` 被误判 cancelled；续传场景在基线回调前失败同理。

## 解决方案

1. **去掉发送前全量哈希**（`src/main/p2p/transfer.ts` `sendFiles`）：只 `stat` 取大小，manifest 的 `sha256` 字段留空串（接收端本就不校验，实际完整性保证不变）。50GB 级传输从「卡 0% 数分钟」变秒开。`hashFile` 保留导出备用。
2. **授权有效期 5 分钟 → 30 分钟**（`src/main/server/service.ts` 新增 `GRANT_TTL_MS = 30 * 60 * 1000`，统一替换 `handleTransferGrant`、`createLocalTransferGrant`、`validateToken` 滑动续期三处硬编码 `5 * 60 * 1000`）。
3. **超时可按方法放宽**（`src/main/client/client.ts` `request` 增加第三参 `timeoutMs = 30000`；`src/main/client/manager.ts` 新增 `LONG_RPC_TIMEOUT_MS = { p2pPush: 10 * 60 * 1000 }`，`ConnectionManager.request` 第四参不传时按方法取默认）——覆盖渲染层发起下载与 `runner.resume` 续传两条 p2pPush 路径，其余 RPC 仍 30s。
4. **失败状态判定修正**：`sendFiles` 新增 `onSent` 回调（每个分块写入 socket 后报数，未 ACK 也计入）；`executePush` 判定改为 `sentBytes > 0 || writtenBytes > 0 || 记录已有 transferred > 0 → 'interrupted'`（保留断点可续传），仅「什么都没发出且磁盘无历史数据」才落 cancelled。
5. **大传输稳定性加固**（顺带）：`DEFAULT_CHUNK_SIZE` 64KB → 512KB（`src/shared/p2p-frames.ts`，载荷 = 12 字节前缀 + data ≤ MAX_FRAME_SIZE=1MB；帧数与逐块开销降 8 倍）；发送分块循环加**背压保护**——`socket.bufferSize > 16MB` 时等 `drain` 再发，防止对端落盘慢时 TCP 缓冲在内存无限积压（大文件可达数 GB 撑爆进程）；drain 后重查 `shouldAbort`。

## 遗留已知行为（未改，供后续决策）

- 发送方（持有文件一方）60 秒内未点「允许接收」确认框，传输按设计自动取消，错误信息「已拒绝或确认超时」——与文件大小无关；若需更友好可加长 `confirmTimeoutMs`（当前 60000，`src/main/index.ts`）或改常驻等待。
- 接收端逐块（现 512KB）`onProgress` 内做一次 `getBySession` SQL 查询，未节流，量级可接受。
