# 收发叫法统一

- 归档日期：2026-11-27
- 类型：需求开发（need）
- 来源：对话归档
- 梳理汇入时间：2026-11-27

## 用户提示词

> 统一名称p2p接收和下载、上传统一一个叫法

澄清问答（选项原话）：

> 统一后的叫法用哪一组？＝"下载 / 上传 (推荐)"
> 改动范围到哪里？＝"UI文案+注释+局部函数名 (推荐)"

## 实际需求梳理

- P2P「接收」与「下载」两个叫法混用、「上传 / 发送 / 推送」三个叫法并存，要求各自统一成一个词。
- 经确认：统一为「下载（文件进入本机）/ 上传（文件离开本机）」，纯用户视角。
- 范围限定：只改 UI 文案、注释、日志、通知与对话框标题、用户可见错误文案；**不动协议字段与记录类型标识符**（`p2pPush`、`p2p-recv`、`ws-recv`、`direction: 'send'/'receive'` 等），避免破坏已存传输记录与断点续传数据兼容。

## 现状调查（归档前扫描结论）

- 中文词频（src 内，不含测试）：接收 75 / 下载 23 / 上传 49 / 发送 33 / 推送 30。
- 英文标识符：`recv` 90 / `receive` 61 / `upload` 系 60+ / `push` 系 55 / `send` 系 40。
- 典型乱象：一条调用链上 `download → p2pPush → prepareReceive → p2p-recv` 串了 4 个叫法；同一动作 WS 通道叫「上传」、P2P 直连叫「发送」、注释里叫「推送」；权限位 `DOWNLOAD` 对应协议方向 `send`（文件所有方视角）与 UI 视角互相打架。
- 事实主干：代码侧「接收/receive」「上传/upload」各自体系完整，「下载」只在 FilesView 文案出现。

## 解决方案与代码变更摘要

原则：进来＝下载，出去＝上传；标识符与"事件推送""socket 分块发送"等编程语义用词保留。共 10 个文件约 70 处：

- `TransfersView.vue`：KIND_META 标签 `P2P 发送→P2P 上传`、`P2P 接收→P2P 下载`、`接收→下载`；相关注释 3 处。
- `SettingsView.vue` + `ServerView.vue`：「接收策略→下载策略」「自动接收→自动下载」（含 tooltip 说明）。
- `index.ts`：对话框「选择接收目录→选择下载目录」、报错「无法启动 P2P 接收端→无法下载文件」、注释 3 处；通知「收到下载请求」本就正确保留。
- `FilesView.vue`：注释 3 处（推送发起失败→下载发起失败、接收端口→下载端口）。
- `protocol.ts`：注释 5 处，记录类型注释明确标注标识符对应（upload=上传 / p2p-send=P2P 上传 / p2p-recv=P2P 下载 / ws-recv=下载）；`direction:'receive'` 注明为"下载方向（对方把文件传到本机）"。
- `service.ts`：注释约 30 处（推送→上传、接收端→下载端等）+ 2 条面板可见错误文案「接收方取消了传输→对方取消了下载」「对方取消了传输→对方取消了上传」。
- `fs-ops.ts`、`transfer-runner.ts`、`p2p/transfer.ts`：注释与 2 条用户可见文案（「接收方向的传输由对端控制…→下载方向」「请在对端（发送方）续传→（上传方）」；DECISION 拒绝理由「接收方拒绝→用户拒绝」避免与上传端报错前缀重复）。

## 有意保留不动的

- 协议字段/记录类型/IPC 名（wire 兼容 + 已存数据兼容）。
- 权限位语义：`DOWNLOAD` ↔ 方向 `send` 仅在 fs-ops 注释补说明「对方从本机下载」。
- 4 个测试文件（e2e/p2p-e2e/transfer-manager/transfer-resume）内部描述文案仍用旧词，纯内部可后续再说。
