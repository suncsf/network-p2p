# 传输临时文件与重名处理

> 归档日期：2026-11-27
> 类型：需求开发（need）
> 来源：AI 助手会话（V-Lattice 项目）
> 梳理汇入时间：2026-11-27 14:41

## 用户提示词

> 1、下载端保存路径如果存在同名文件提示：覆盖、重命名、取消
> 2、下载或接收端接收文件时，先生成临时文件.tmp，接收完再更名为正式名称，覆盖的将同名文件删除再更名
> 2、取消传输 接收端需要把生成的临时文件删除

（原话第二条重复编号"2"，为口误，实为第 3 条需求；梳理时不修改原话。）

## 实际需求梳理

1. 下载端在选定保存路径后，若目标位置存在同名文件/目录，弹出提示让用户三选一：覆盖（照常下载，完成后替换旧文件）、重命名（自动生成不重复的新名称）、取消（放弃本次下载）。
2. 接收端（P2P 下载 + WS 接收）落盘时先写 `.tmp` 临时文件，全部接收完成后再更名为正式名称；「覆盖」场景在更名前先删除同名旧文件再更名（Windows 的 rename 不覆盖已存在文件）。
3. 用户取消传输时，接收端把已生成的 `.tmp` 临时文件删除；网络中断则保留 `.tmp` 用于断点续传。

## 解决方案

### 1. 重名冲突提示（src/main/index.ts p2p:prepareReceive）

- 目录/批量下载选定目录后，对每个目标项 `existsSync(join(localDir, target))` 检查重名；有冲突时 `dialog.showMessageBox` 三按钮（覆盖 defaultId=0 / 重命名 / 取消 cancelId=2），列出前 8 个冲突项。
- 选「重命名」时由新增模块级函数 `uniqueTargetName()` 生成不重复新名：文件保留扩展名 `a (1).txt`、目录 `a (1)`，与现有文件及其他已重命名项（taken 表）双重查重；生成 `renameMap`（远端相对路径前缀 → 本地相对路径前缀）。
- `renameMap` 存入下载授权（`createLocalTransferGrant` 新增 opts.renameMap）与传输记录续传上下文（recvResume 新增 renameMap 字段）；续传授权兜底重建时原样携带。
- 单文件下载仍走系统保存对话框（原生自带覆盖确认），不重复弹窗。

### 2. .tmp 临时文件与完成更名（src/main/p2p/transfer.ts + src/main/server/fs-ops.ts）

- P2P 接收端：CHUNK 落盘路径改为 `正式名 + '.tmp'`；DONE 后 `finalizeFiles()` 统一更名——先 `rm(abs, {force:true})` 删同名旧文件再 `rename(tmp, abs)`；零字节文件无分块，完成时直接补建空文件。
- 续传偏移改按 `.tmp` 文件 `stat().size` 计算（原按正式文件）。
- 新增 `resolveTarget()`：统一应用 `mapRelPath` 重命名映射 + 路径安全校验（拒绝 `..`、绝对路径、越界），MANIFEST 续传统计 / CHUNK 落盘 / DONE 更名三处共用。
- service.ts 的 createReceiveServer 新增 `mapRelPath(sessionId, relPath)` 接线：按授权里的 renameMap 做最长前缀匹配替换（目录级整体重命名）。
- WS 接收路径同步改造：`createUpload` 打开 `abs + '.tmp'`，`finishUpload` 关句柄后删旧文件再更名，`abortUpload` 删 `.tmp`。

### 3. 取消清理临时文件（transfer.ts + service.ts）

- `createReceiveServer` 返回值升级为 `P2PReceiveServer`（net.Server + `markCancelled(sessionId)`）；内部 `cancelledSessions` 集合，socket close 且该会话被标记时 `cleanupTmp()` 删除 manifest 全部 `.tmp`。
- `LatticeServer.abortReceive()`（传输面板「取消」）先 `markCancelled` 再 destroy——这是用户取消语义；网络中断（对端断开/发送端 cancelPush）不标记，`.tmp` 保留可续传。

### 4. 连带修复的产品级 bug：帧处理串行化（transfer.ts，重要）

- 根因：FrameParser 对每帧同步调用 async 的 `onFrame` 但不 await，小文件的全部帧（CHUNK×N + DONE）挤在同一次 data 事件里并发处理，DONE 的 finalize 在 CHUNK 落盘前执行（`.tmp` 尚不存在），导致**小文件传输完成后正式文件永远不出现**（旧代码直接写正式文件所以未暴露）。
- 修复：`frameQueue` 按到达顺序串行处理帧（`frameQueue.then(() => handleFrame())` 链），`frameFatal` 标志在致命错误后停止后续帧；socket close 的收尾（onInterrupted 通知 / 关句柄 / 取消清理）也挂到 `frameQueue` 之后，避免把已完成传输误报为中断、或提前关闭仍在写的句柄。
- 顺带：mkdir 从每块动态 import 提为模块级静态导入。

## 代码变更摘要 / 关键结论

- 用户取消（abortReceive）与网络中断（cancelPush / 对端断开）语义正式分离：前者清理 `.tmp`，后者保留断点。
- 发送端「completed」只代表写完 socket，不等待接收端落盘更名——测试断言最终文件必须轮询（实测滞后约 13ms）。
- 回环传输 12MB 可在 5ms 轮询间隔内完成，测试捕捉中间态需 setImmediate 高频采样。
- 暂停后仍有 TCP 在途分块继续落盘，冻结断言前需等落盘稳定。
- typecheck 0 错误；测试从一度 12 项失败修至 55 项全绿（连续两轮稳定通过）；改动未提交 git。
